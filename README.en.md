DeepSeek Harness for Codex lets Codex start [DeepSeek Harness](https://github.com/deepseek-ai/DeepSeek-Harness) locally, return a clickable live-session link, delegate work to it, and then independently review the resulting workspace changes.

## Quick start

Use the Codex plugin unless you specifically need a standalone MCP server. The plugin installs both the MCP tools and the instructions that tell Codex to review Harness's work independently.

### 1. Check the requirements

- Node.js `^22.19.0 || >=24.0.0`, including the `npm` that ships with Node (used for the one-time runtime package install)
- A Codex client with plugin support
- A DeepSeek API key

Put the API key in the target repository's ignored `.env` file:

```dotenv
DEEPSEEK_API_KEY=your-key
```

Do not commit this file. You can instead provide `DEEPSEEK_API_KEY` to the environment that starts Codex, or configure the key later in the opened Harness page under **Settings → Models**.

### 2. Install the plugin (recommended: local path)

This repository root *is* the Codex plugin (`.codex-plugin/plugin.json` + `.mcp.json` + `skills/`),
but `dist/` has to be built first — Codex only copies files and never builds for you. Prepare a local checkout:

```sh
git clone https://github.com/Seann0824/deepseek-harness-for-codex.git
cd deepseek-harness-for-codex
npm install
npm run prepare:plugin
codex plugin marketplace add "$PWD"
codex plugin add deepseek-harness@deepseek-harness-for-codex
```

On Windows PowerShell use `codex plugin marketplace add (Get-Location).Path`.

`npm run prepare:plugin` runs the full `npm run check` (typecheck, tests, build, metadata gate) and generates
`plugins/deepseek-harness/`, the payload the marketplace installs. **Do not skip it**: without it the
marketplace resolves to a plugin directory with no `dist/bin.mjs`.

A locally installed plugin executes the `dist/bin.mjs` that ships with it (`node ./dist/bin.mjs`), never
`npx`, so it does not depend on any published npm version.

### Optional: install from the npm source

Use this path only when the registry actually holds a version matching this repository (the package name is not
exclusive to this repository, and the published version may lag behind it; the current repository version is
in `package.json`). Installing from npm requires the marketplace `source` to point at a published package, so it
is **not** a works-out-of-the-box path for this repository: first publish the plugin under a package name you
control (see the open decision in `docs/decisions/ADR-0001-distribution-and-version-ssot.md`), then switch the
marketplace `source` from the local path to that package. After that:

```sh
codex plugin marketplace add <your marketplace repo or package name>
codex plugin add deepseek-harness@deepseek-harness-for-codex
```

**Do not** run `marketplace add Seann0824/deepseek-harness-for-codex --ref main`: the marketplace payload
`plugins/deepseek-harness/` is a build artifact and is not committed, so a fresh clone has nothing to install.
Distributing over git requires running `npm install && npm run prepare:plugin` inside the clone first (the
canonical path above), or switching to the "commit the generated payload" distribution shape.

### Local checkout (canonical) vs git source

`plugins/deepseek-harness/` is generated by `npm run version:sync` from `package.json` and is therefore
git-ignored: **committing a generated copy creates a second version fact** (which is exactly how this repository
previously ended up with 0.3.1 and 0.4.0 coexisting and silently downgrading). The cost is that a git-source
install must prepare the checkout once. If "clone and install" is ever required, commit the generated
directory — the gate verifies it byte-for-byte, so drift cannot come back.

On macOS, if `codex` is not found or another global installation shadows the desktop client, use the executable bundled with the app:

```sh
CODEX_APP_BIN="/Applications/ChatGPT.app/Contents/Resources/codex"
"$CODEX_APP_BIN" plugin marketplace add "$PWD"
"$CODEX_APP_BIN" plugin add deepseek-harness@deepseek-harness-for-codex
```

### 3. Start a new Codex task

Plugins are loaded when a task starts. Create a new task in Codex and ask it to use DeepSeek Harness, for example:

> Use DeepSeek Harness to implement this change in a visible local session. Do not open my browser automatically; give me the live Harness page link, then review the diff and run the relevant checks yourself.

Codex will start Harness locally, serve its Web page on a free loopback port, return a clickable link, submit the task, follow the visible session, and independently verify the result. The browser does not open automatically; click the link in Codex when you want to watch. You do not need to run Harness or register a separate MCP server.

The first task downloads only the pinned Harness runtime package (`@deepseek-ai/dsh`); the MCP server itself
ships with the plugin and is no longer fetched from the registry.

## How it works

The plugin launches the MCP server that ships with it via `node ./dist/bin.mjs` (never `npx`, so a plugin install can never silently pull an older release). On the first task for a workspace, the MCP server installs the exact DSH runtime into `<DSH_MCP_DATA_DIR>/versions/<version>/` (a one-off cost) and then starts it as `node <that directory>/node_modules/@deepseek-ai/dsh/lib/bin.js web --no-open --port 0` on loopback so DSH does not open a browser itself. Codex creates the workspace and session through the current Harness Web API and presents the URL as a clickable link. The service exchanges DSH's launch URL for the local API cookie. The link contains a local login token; do not share it publicly. Later tasks reuse that local service. The task does not run on a hosted bridge.

Each run is fresh and asynchronous:

1. Codex calls `start_run` with an absolute workspace and a complete task.
2. The MCP server starts or reuses Harness Web (performing the one-off runtime install first, if needed), submits a visible session, and returns its page URL to Codex.
3. Codex presents a clickable link; the user opens it when needed while Codex follows the same session with `wait_run` or `get_run`.
4. Codex inspects the resulting diff and runs its own verification.

## MCP tools

| Tool | Purpose |
| --- | --- |
| `doctor` | Check the Node engine range, the npm CLI, the installed runtime package, proxy variables, credential visibility, data location, and workspace restrictions without installing or downloading anything. |
| `start_service` | Start or reuse Harness Web for a workspace and return its URL without opening the browser by default. |
| `open_service` | Open a running Harness page when the user explicitly requests it. |
| `list_services` | List local Harness Web services and URLs. |
| `stop_service` | Stop a Harness Web service. |
| `start_run` | Create a new visible session or continue a completed session selected by Codex, then submit a task. |
| `wait_run` | Wait up to 30 seconds for the visible session. **Repeatable and side-effect free**: a finished run keeps returning the same terminal snapshot, and a timeout returns the current snapshot instead of failing. |
| `get_run` | Read state and assistant text from the Web session. |
| `list_runs` | List runs owned by the current MCP server process. |
| `cancel_run` | Cancel the agent turn while keeping Web available. |

Both `start_service` and `start_run` default `openBrowser` to `false`, and the plugin explicitly passes `false`. Codex should render the returned `webUrl` as a clickable link; it should use `open_service` only when the user explicitly asks Codex to open the page.

Run status and failure reasons (`RunSnapshot`):

- `status` has exactly four values: `running` / `succeeded` / `failed` / `cancelled`. **Only a `completed` turn counts as `succeeded`.** A run never stays `running` on a failure path.
- `reason` is set only when `failed`, and says *why*: `auth` (the credential was rejected twice), `service-unreachable` (cannot connect, or the service died mid-turn), `protocol-drift` (the Host's answer violates the contract; carries the method and JSON path), `rpc:<code>` (a business error code from the Host), `turn-blocked` (the turn was refused before any step), `turn-truncated` (output hit the token limit), `turn-aborted:<cause>` (aborted by parent/hook/disposed/legacy), `turn-interrupted` (synthesized after a crash), `turn-unknown:<kind>` (a reason this project does not recognize — always a failure).
- Cancellation: a user cancellation (`cancel_run` or the Web UI) converges to `cancelled`, as does an `aborted` whose cause is `user`. `blocked` and `max-tokens` are failures now; older versions reported them as successes.
- `nextAction`: the next step, **derived one-way from `reason`**, over a closed set of six values — `new-session` (start a fresh session and retry: `turn-blocked`, a turn rejected before any step ran, where there is nothing to narrow), `retry-narrower` (narrow the task and try again: `turn-truncated`, output cut off by the token limit), `restart-service` (restart the service and retry: `service-unreachable` / `transport`), `relogin` (call `start_service` again for a fresh credential: `auth`), `report-only` (report, do not guess an action: `protocol-drift`, `turn-interrupted`, plus **every open family** `rpc:<code>` / `turn-aborted:<cause>` / `turn-unknown:<kind>`), and `none` (`reason` is empty, i.e. `running` / `succeeded` / `cancelled`). Open families are **always** `report-only`: a failure this project does not recognize may never be guessed into a concrete action. `turn-interrupted` belongs to the same "do not guess" group: it is DSH's **crash recovery** over a persisted log (missing `step/end`, `turn/end` are supplied as synthetic events) and the session is then **resumed in place**, so "the old session is unusable" is not a fact we have verified.
- `webUrlStale`: `true` **only** for `failed(service-unreachable)`. **A service restart reassigns the port and rotates the launch token, so the old link dies with it** — do not reuse the old `webUrl`; call `start_service` again for a fresh link.
- `progress`: a **numbers-only** projection of what a long turn is doing — `{started, finished, current}`, where `current` is `{turn, step, seq}` or `null`. It deliberately carries **no** tool name, argument, command or output: no recording proves a tool name (a `step/start` payload holds only `{turn, step}`), so this project **does not guess** the field — showing less beats letting argument text reach a snapshot or a log. Polling tightens to **150 ms** while events arrive and backs off to **400 ms** when silent (a bounded pure function: ≈7 polls/second worst case).

**The default permission mode requires manual approval**: the default `DSH_PERMISSION_MODE=workspace-write` maps to `approval: ask` (see `packages/bundle/base/cordis.patch.yml`) — any action that writes files or runs commands waits for you to approve it in the Harness page, and the MCP surface **cannot answer that prompt for you**. From Codex's point of view such a run simply stays `running` for a long time. Approve it in the page, or explicitly use `DSH_PERMISSION_MODE=danger-full-access` in a controlled environment.

## Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `DSH_MCP_DATA_DIR` | `~/.deep-seek-harness-mcp` | Data directory: `versions/<version>/` holds the locally installed Harness runtime package, `services/<workspace hash>/` holds each workspace's DSH_HOME (sessions and settings). **The location guard resolves aliases**: a symbolic link or junction that points at the user's home directory (or a directory inside it) is refused, and a failed resolution (a symlink loop, for instance) is refused too — "cannot resolve" is not evidence of safety. An explicitly written `~/.deep-seek-harness-mcp` layout is unaffected. |
| `DSH_MCP_HARNESS_PACKAGE` | `@deepseek-ai/dsh@0.2.1-alpha.1` | The **exact** npm spec for the local Harness runtime (it must be written `name@x.y.z`). Ranges (`^`, `~`, `>`, `x`, `*`) and dist-tags (`latest`, `next`) are **rejected**: the registry's `latest` is older than this project's release line, so resolving a range would silently downgrade. |
| `DSH_MCP_NPM_CLI` | derived from `process.execPath` | Absolute path of `npm-cli.js`. npm is always invoked as `node <that file> install …` with `shell: false` (never through `npm.cmd`, so there is no shell injection surface). Set it only when the derivation fails; a relative or missing path fails immediately. |
| `DSH_MCP_INSTALL_TIMEOUT_MS` | `900000` | One-off install budget for the runtime package, independent of the startup budget (install progress resets it). |
| `DSH_MCP_STARTUP_TIMEOUT_MS` | `180000` | **Silence** budget between process start and the URL line: every line of child output resets it, so progress is never a timeout — only total silence is. |
| `DSH_MCP_RUN_LIMIT` | `4` | Concurrent runs per process (across workspaces; within **a single MCP process on one data directory**, a single workspace allows one at a time). Exceeding it is **rejected with an actionable error** rather than queued — no run record is created, so there is no `queued` status. **Both the limit and workspace serialization are in-process**: two MCP processes sharing a data directory count separately (cross-process quota is explicitly not implemented; cross-process safety comes from the service structure and `runs/.adopt.lock`). |
| `DSH_MCP_WORKSPACE_ROOTS` | unrestricted | Platform-delimited absolute roots that may be passed to `start_run`. |
| `DSH_PERMISSION_MODE` | `workspace-write` | DSH permission mode. **The default maps to `approval: ask`**: any action that writes files or runs commands waits for manual approval in the Harness page, which the MCP surface cannot answer (see `docs/operations.md` §7). Use `read-only` for review-only tasks; only `danger-full-access` becomes `approval: never`, and the caller must pass it explicitly. `doctor.permission` reports the effective mode, its source, and the approval policy. |
| `DSH_TELEMETRY_DISABLED` | `1` | Passed to the Harness child; telemetry is off by default. |
| `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL` | unset / provider default | Optional DeepSeek credentials and compatible API endpoint. |
| ~~`DSH_MCP_NPX_COMMAND`~~ | **removed** | The launch vector no longer uses npx. If it is still set, `doctor` reports it as deprecated and ignored, with a migration hint. |

Data directory layout and first-run cost:

```text
<DSH_MCP_DATA_DIR>/
├─ versions/
│  └─ <dsh version>/                   # locally installed runtime package (~486 MB/version, enumerable)
│     └─ node_modules/@deepseek-ai/dsh/lib/bin.js
└─ services/<workspace hash>/           # that workspace's DSH_HOME (sessions, settings, credential references)
```

The first task for a given DSH version runs `node <npm-cli.js> install --prefix <temp dir> … <exact spec>` once and **atomically renames** the temporary directory to `versions/<version>/`. Every later start is `node <bin> web --no-open --port 0` with `shell: false` — npm is not invoked again and no network is needed. The install is a one-off cost (about a minute; mostly 486 MB of files — measured 54 s / 486.1 MB with a warm npm cache), which is why it uses the separate 900-second budget and never counts against startup. Startup itself has three cases: **installed, but with an empty DSH home (a true cold start) takes about 20–30 s** (measured 22.7 s; independent acceptance measured 29.4 s), **about 4 s once the DSH home is warm** (measured 3.8–4.1 s), and reusing an installed runtime is a millisecond-level check that downloads nothing.

Telemetry is disabled for Harness child processes by default. The Web service binds to loopback and selects a free port. Session data remains in the configured data directory for local audit.

`doctor` field reference (each maps to a row above):

| Field | Meaning |
| --- | --- |
| `version` | The version of **this MCP server** (currently the `package.json` version). |
| `engines` | `{range, nodeVersion, supported, source}`; the range is declared by this project. |
| `runtimePackage` | `{spec, installed, version, root, binPath, diskBytes, error}` — the resolved state of `DSH_MCP_HARNESS_PACKAGE`; a non-null `error` means the spec is invalid. |
| `harnessPackage` | An alias of `runtimePackage.spec`: the DSH runtime spec that will be **installed and launched** (the current `DSH_MCP_HARNESS_PACKAGE` value). It is **not** this server's version — use `version` for that. |
| `npmCli` | `{path, source, exists}` — the resolved `DSH_MCP_NPM_CLI` and how it was found (PATH is never consulted). |
| `dataDirectory` | `{path, source, exists, writable}`. `source` ∈ `DSH_MCP_DATA_DIR`/`PLUGIN_DATA`/`default` (which setting chose the path); when `exists` is false, `writable` is necessarily `unknown`. Only an **existing** directory gets the real create-and-delete probe (`yes`/`no`); a missing one reports `unknown` and is **never created** (the first install creates it). |
| `proxy` | `{env, noProxy}`, reported without judgement. |
| `deprecatedEnv` | Variables that are still set but deprecated and ignored (such as `DSH_MCP_NPX_COMMAND`). |
| `ready` | `engines.supported && npmCli.exists && dataDirectory.writable !== "no" && runtimePackage.error === null`. **Those four terms only**: reporting fields (such as `orphans` and `permission`) never change it. It installs nothing, downloads nothing, and probes no network. |
| `problems` | `string[]`: every entry pairs a problem with its fix. Two kinds: ① an unmet prerequisite (Node outside the range / npm CLI missing or not an absolute path / data directory not writable / invalid runtime package spec) — these always imply `ready: false`; ② an **advisory** finding (for example orphaned service processes). An **empty array means there is nothing to report**, and a false `ready` always comes with a kind-① entry. `runtimePackage.error` remains the detail layer. |
| `orphans` | `Array<{pid, port, serviceHome, state}>`: service state a previous run left behind (`<dataDir>/services/<key>/dsh.pid`). `state`: `alive` — the process is up **and confirmed to be ours** (its command line carries our `lib/bin.js` and `--port`); `unverified` — it is up but its **identity cannot be confirmed** (it is never killed by pid alone: a recycled pid would be somebody else's process); `stale-pidfile` — the file exists but the process is gone, or the file is corrupt. `[]` when there is nothing. The next `start_service` reclaims confirmed orphans automatically and keeps the evidence when it cannot. |
| `nodeVersion` / `nodeSupported` | The running Node version and whether it falls inside the supported range (flat copies of `engines`, for a one-glance check). |
| `platform` / `architecture` | Runtime platform and architecture (such as `win32`/`darwin`/`linux` and `x64`/`arm64`). |
| `apiKeyInEnvironment` | Whether `DEEPSEEK_API_KEY` is visible in the host environment: a **boolean only**, whose value is never read or echoed. |
| `allowedWorkspaceRoots` | The resolved `DSH_MCP_WORKSPACE_ROOTS`: an **empty array (`[]`) when unset** — that is how "unrestricted" is spelled, never `null`; when configured, the roots split on the platform delimiter (legality is still checked against the workspace policy when `start_run` runs). |
| `permission` | `{mode, source, approval, advisory}` for the next Harness launch. `source`: `env` (you set `DSH_PERMISSION_MODE`) or `default` (`workspace-write`); `approval`: derived exactly as DSH derives it (only `danger-full-access` is `never`, everything else is `ask`); `advisory`: an actionable sentence when `ask` (a human must approve in the Harness page and this MCP server cannot answer that prompt), `null` when `never`. **It is a report, not a prerequisite**: it never changes `ready`. |
| `contract` | Contract-matrix verdict: `dshLine`, `installedVersion` (the resolved full version, `null` when nothing resolved), `status` (`exact`/`compatible`/`unknown`/`unsupported`), `baselineDshLine`, `recordedVersions`, `differences` (versus the baseline; `null` for an unrecorded line), and `detail`. Only `unsupported` enters `problems` and affects `ready` (`unknown` is the ordinary "nothing installed yet" state and is deliberately not a failure). |
| `surface` | The interaction surface this server offers; always `web` today. |

## Troubleshooting

Start with `doctor`. It installs and downloads nothing and reports: the Node engine range (`^22.19.0 || >=24.0.0`, declared by this project because the published `@deepseek-ai/dsh` has no `engines` field), the resolved npm CLI path and how it was found, whether the runtime package is installed (version / path / disk usage), the data directory, proxy variables (reported, not judged), and deprecated environment variables.

**Install failures** carry the npm `npm error code …` stderr tail, the runtime package path, and an actionable hint. Handle them by code:

| npm error code | Meaning | Action |
| --- | --- | --- |
| `ETARGET` / `E404` | That version does not exist on the registry (**no retry**) | Check `DSH_MCP_HARNESS_PACKAGE` against `node <npm-cli.js> view <package> versions` |
| `ENOTCACHED` | npm has no cached copy (offline or not pre-warmed) | Connect once, or pre-warm: `node <npm-cli.js> cache add "<spec>"` |
| anything else (network / registry) | Classified as network and **retried once automatically** | Check proxies and mirrors (`npm_config_registry`, `HTTPS_PROXY`); use `DSH_MCP_NPM_CLI` to point at a working npm |

To pre-warm and skip the first-run wait, install directly into the version directory:

```sh
node "<npm-cli.js>" install --prefix "<DSH_MCP_DATA_DIR>/versions/<version>" --no-save --no-audit --no-fund "@deepseek-ai/dsh@<version>"
```

**Startup timeouts** are measured as silence, and the failure message carries the redacted Harness log tail, the runtime package path, and the npm stderr tail. If the log keeps printing without a `dsh web: http://…` line, raise `DSH_MCP_STARTUP_TIMEOUT_MS` or check that DSH_HOME is writable; if the log is empty, use `doctor` to confirm the runtime package and npm CLI are usable.

## Security model

`start_run` is a write-capable tool. The server requires an existing absolute workspace (symlinks are resolved) and can restrict allowed roots with `DSH_MCP_WORKSPACE_ROOTS`. When a session is reused, the Host must report that session's `cwd` and it must match this workspace — **if ownership cannot be proven the reuse is refused** (fail closed) instead of let through.

There is exactly **one** intentional carrier for the credential: the login URL returned to the caller (it is the local bearer credential the user clicks). Every other exit — startup/readiness log tails, error text, service and run snapshots, `doctor` output, and every tool result — passes through one redaction boundary (token and cookie values become `[redacted]`), and tool results are scrubbed again at the MCP boundary. No cookie value ever appears in output. The all-exits scan (`tests/security-exits.test.ts`) turns red if any of that regresses.

Loopback only: a launch URL that is not loopback (`127.0.0.0/8`, `::1`, `localhost`) is refused as a credential exchange target, and loopback requests never go through the environment proxy (pointing `HTTP_PROXY` at a dead address changes nothing). The Harness itself is started as `process.execPath` plus the installed package's `lib/bin.js` with `shell: false` throughout (there is no `npx.cmd`/`cmd.exe` layer any more), and the npm spec must be an exact version, so no shell-interpreted external input exists. The default permission mode is `workspace-write`. DSH's Windows `workspace-write` mode may leave persistent ACL marks on the workspace; use a disposable worktree when the project must remain shared with other tools.

The contract with the Host requires only the fields we actually read (for example `session/list#cwd` and `turn/end#reason`) to exist and be correctly typed: a missing or mistyped one is protocol drift and fails closed, while extra fields are always allowed — that is how the protocol evolves.

## Session model

Every `start_run` lets Codex choose the session. Omitting `sessionId` creates a new visible Harness session. Passing a completed `sessionId` from an earlier run continues that conversation while returning only the new turn's output. A running session cannot be reused concurrently. The Web service is reused for later tasks in the same workspace until `stop_service` or MCP shutdown.

## Version and metadata (single source of truth)

`package.json` name/version is the **only** version fact; everything else is derived:

| File | Source |
| --- | --- |
| `src/version.ts` | generated by `npm run version:sync` (header says generated, never edit) |
| `.mcp.json`, `.codex-plugin/plugin.json` | same generator, version taken from `package.json` |
| `plugins/deepseek-harness/**` (marketplace payload) | same generator; the directory is **git-ignored** and only exists after generation |
| README / SKILL version wording | no hardcoded pins, so it cannot drift (the gate rejects any version pin) |

```sh
npm run version:sync     # regenerate (writes)
npm run version:check    # verify only, never writes, lists drift with expected values
npm run check-metadata   # packaging gate: versions + files[] whitelist + launch shape + plugin payload
npm run prepare:plugin   # build + generate + full check (required before installing the plugin locally)
```

`npm run check` includes the metadata gate: tampering with any version, the `files[]` whitelist, the launch
shape, or the generated payload makes `check` fail with the expected value. Generated-and-ignored was chosen
over commit-then-sync because two committed copies always diverge again (that is exactly how this repository
once ran an older release), while an ignored generated tree can never become a second version fact.

## Local development

Clone the repository, build it and generate the plugin payload, then add the checkout as a local marketplace:

```sh
npm install
npm run prepare:plugin
codex plugin marketplace add /absolute/path/to/deepseek-harness-for-codex
codex plugin add deepseek-harness@deepseek-harness-for-codex
```

The plugin runs the generated `plugins/deepseek-harness/dist/bin.mjs`; **no** manual `.mcp.json` edit with an
absolute path is needed any more. Two caveats:

- Codex copies plugin files into its own cache, keyed by plugin version; after changing content, re-run
  `npm run prepare:plugin` and bump `package.json` `version` (or clear the cache directory) so it copies again.
- Edits under `plugins/deepseek-harness/` are not preserved: the next `build`/`prepare:plugin` regenerates it
  and the gate reports hand-added files as extras.

## Publishing the npm package

This repository publishes the public, unscoped `deepseek-harness-for-codex` package to the official npm registry. `npm publish` automatically runs the typecheck, test, build and metadata gate. The package contains `dist/` (a self-contained bundle with runtime dependencies inlined), `.codex-plugin/plugin.json`, `.mcp.json`, `skills/`, both README files, the demo GIF and `LICENSE`.

Authenticate and verify the account:

```sh
npm login --registry=https://registry.npmjs.org/
```

An npm version cannot be overwritten. For a new release, change **only** `package.json`; every other version
reference is derived:

```sh
npm version patch          # or minor / major: touches package.json and package-lock.json only
npm run prepare:plugin     # regenerate src/version.ts, .mcp.json, plugin manifests and the marketplace payload
npm publish
```

Never hand-edit `src/version.ts`, `.mcp.json`, `.codex-plugin/plugin.json` or `plugins/deepseek-harness/**`;
`npm run check` detects and rejects that.
